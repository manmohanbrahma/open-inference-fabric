# P1.4 Lab Acceptance Checks — Topology & Intent

**Related:** ADR-019, ADR-020, TASKS.md (T-130 – T-136), docs/design/Vendor-Agnostic-Job-Model.md  
**Style:** Matches existing lab scripts (`t121-cluster.sh`, `t122-gpus.sh`): numbered checks, clear counts, runnable on hybrid-gpu-lab and (where noted) the reference host.

---

## Environments

| Environment | What it proves |
|-------------|----------------|
| **hybrid-gpu-lab** | Multi-node domains (one NVIDIA worker, one AMD worker), domain packing, HA regression |
| **Reference host** | Single-node domains, AIJob façade, dual-vendor ResourceQuota interaction, clean uninstall |

NVIDIA DSX is **not** used as a pass/fail gate for these checks (ADR-020).

## T-130 / T-131 — Topology discovery & AcceleratorDomain

**Script sketch:** `tests/lab/t130-topology.sh`

| # | Check | Pass condition |
|---|-------|----------------|
| 1 | Nodes Ready | All expected nodes report Ready |
| 2 | Vendor labels present | GPU workers have `oif.accelerator/vendor=nvidia` or `amd` (or equivalent) |
| 3 | Interconnect class labelled | Nodes carry an interconnect/bandwidth class label (even if `pcie` or `unknown`) |
| 4 | AcceleratorDomain objects exist | At least one domain for the NVIDIA worker and one for the AMD worker |
| 5 | Domain vendor matches | Each domain’s `spec.vendor` matches the GPUs it contains |
| 6 | Domain capacity | `status.capacity.gpu` equals the number of GPUs in the domain |
| 7 | Single-node domains (reference host) | On the dual-GPU host, two domains (or one mixed-aware view) appear and list the correct devices |
| 8 | Idempotent | Re-running discovery does not create duplicate domains |

**Suggested count:** 8 checks (lab) / 6+ checks (reference host subset).

## T-132 — Domain-aware packing

**Script sketch:** `tests/lab/t132-domain-pack.sh`

| # | Check | Pass condition |
|---|-------|----------------|
| 1 | Same-domain multi-GPU job | An AIJob (or equivalent multi-GPU workload) with `requireSameDomain: true` and gpuCount that fits one worker lands entirely on one domain |
| 2 | Status records domain | Job status shows the chosen `domain` and `vendor` |
| 3 | CrossVendor false | Status `crossVendor` is false |
| 4 | Oversized same-domain request | A request larger than any single domain with `requireSameDomain: true` remains Pending (or fails with a clear condition), does not silently split |
| 5 | Regression: existing pools | Direct `nvidia.com/gpu` / `amd.com/gpu` pods still schedule on the correct workers |

**Suggested count:** 5 checks.

## T-133 / T-134 — AIJob façade & PlacementPolicy

**Script sketch:** `tests/lab/t133-aijob.sh`

| # | Check | Pass condition |
|---|-------|----------------|
| 1 | Vendor-agnostic submit | An AIJob with **no** vendor field is accepted and becomes Running (or Pending for capacity) |
| 2 | Translation | Underlying Run:ai / Kubernetes objects are created (project, workload, or pod) with a concrete resource name |
| 3 | preferVendor respected | Soft preference influences placement when both vendors have capacity |
| 4 | allowCrossVendor false | Job with `allowCrossVendor: false` never spans vendors |
| 5 | PlacementPolicy default | Namespace (or cluster) PlacementPolicy supplies defaults when the AIJob omits fields |
| 6 | Status completeness | Status contains `vendor`, `domain` (when known), `crossVendor` |
| 7 | Direct jobs still work | A plain pod requesting `nvidia.com/gpu` or `amd.com/gpu` is unaffected |

**Suggested count:** 7 checks.

## Implementation notes

- Prefer the same shell style as `t121-cluster.sh` / `t122-gpus.sh` (setup, numbered checks, summary count).
- Use the cluster SSH key and node list already established by T-120/T-121.
- Keep secrets and lab addresses out of Git; read from the environment / oif state.
- When a check needs an AIJob CRD that is not yet implemented, the script may temporarily drive the underlying Run:ai objects and assert the *intent* of the future façade; replace with real CRD calls once T-133 lands.
